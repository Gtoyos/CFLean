# The formal model

How the paper's notions are formalized in Lean. Names in backticks are
declarations in `CFLeanProof/`, in the namespace `ConflictFreedom`.
[`Paper.lean`](CFLeanProof/Paper.lean) restates each definition below next to
the paper's wording, and states every numbered result.

## Trusted base

Lean's kernel, its standard library, and the definitions below, which a reader
must check against the paper. No result takes a hypothesis the paper does not
state. Algorithm 2 runs on atomic snapshot objects, as in the paper; their
implementation from read/write registers is cited from the literature, not
formalized (see [Assumptions](#assumptions)).

## Objects and conflicts (§3.1)

- `Object State Op Response`: a sequential object `(Q, q₀, O, R, σ)`, with
  `initial = q₀` and `step = σ`.
- `CommuteAt a b q`: from `q`, `a` then `b` and `b` then `a` give the same two
  responses and the same final state. `Paper.commuteAt_iff` shows it is the
  paper's existential definition.
- `Independent a b`: `a` and `b` commute in every state. `Conflict a b`
  (`a ≍ b`): they fail to commute in some state, reachable or not.

## Executions and progress conditions (§3)

The progress conditions are stated over operation-level executions, as the
paper states them: what matters is which operation instances are invoked, which
complete, and which take each step.

- `Execution n Op`: an infinite execution of `n` processes (`Fin n`). It has a
  type of operation instances, each with an operation, an owner process, an
  invocation time and possibly a response time, and at each instant the instance
  that takes a step, if any. Each process has at most one pending instance at a
  time (`sequential`), and an instance takes steps only while pending. `live`
  makes the execution infinite: some instance steps at arbitrarily late times.
  There is no fairness, and any number of processes may stop.
- `Correct p`: `p` takes infinitely many steps, or has no pending operation.
  `Solo i`: `i` completes, or from some time on only `i` takes steps
  (eventually step-contention free). `EventuallyConflictFree`: from some time
  on, no two concurrent instances (pending at a common time) have conflicting
  operations.
- `Implementation n Op`: the set of executions an implementation admits. The
  progress conditions quantify over it.

| Paper | Lean |
|---|---|
| wait-free, lock-free, obstruction-free | `WaitFree`, `LockFree`, `ObstructionFree` |
| Definition 3.1 (conflict-freedom) | `ConflictFree A conflict` |
| Definition 3.2 (weak conflict-freedom) | `WeakConflictFree A conflict` |
| Propositions 3.3, 3.4 | `progressHierarchy`, `universal_*_iff_obstructionFree`, `empty_conflictFree_iff_waitFree`, `empty_weakConflictFree_iff_lockFree` |

`WaitFree` requires every correct process to complete its operations; the
paper's reading, every correct process *taking infinitely many steps*, is
equivalent (`waitFree_iff_infiniteSteps`). With `n = 0` there is no execution
(`Execution.false_of_zero`), so every progress condition holds vacuously; the
theorems that the admitted sets are non-empty are for `n = m + 1`.

## Schedules and traces (§4.1)

- A schedule is a `List Op`. `TraceEq`, the relation generated by swapping
  adjacent independent operations, is the paper's `∼`: `traceEq_iff_scheduleEquiv`
  identifies it with `ScheduleEquiv`, conditions (i) and (ii) of the paper
  verbatim.
- `Trace`: the quotient `O*/∼`. `traceAppend` is concatenation, `TracePrefix`
  is `≤`, `Compatible` is `comp(S)`; `glb_exists` and `lub_exists` give `⊓` and
  `⊔` of compatible families.
- `responses o s q` lists the responses of the occurrences of `o` in `s` from
  `q`, so its `i`-th entry is `ret*(o⁽ⁱ⁾, s)`; `traceReturn` is its reading on
  traces.

## Generalized Commit-Adopt (§4.2)

- `GCA.History obj P`: one GCA object in one execution — each participant's
  input `s_i`, and its output `(t_i, c_i)` once its call has returned.
- `GCA.History.Specification`: the six properties, each as the paper states it
  (`Validity`, `Adoption`, `Commitment`, `Convergence`, `CommonPrefix`,
  `WeakAgreement`). Validity is the multiset inclusion
  `ops(t_i) ⊆ ⋃ ops(s_j)`; Commitment carries the paper's guard `P ≠ ∅`; Common
  Prefix is stated for every common lower bound of the inputs, which is
  equivalent to the paper's `⊓`.
- `GCAMachine O n`: any GCA implementation, serving every round, as an abstract
  machine — a state, a step of a caller's current call, the output once the
  call has finished, and the state after the caller returns. Nothing else is
  fixed: not its shared objects, nor how many steps a call takes.
- `GCAMachine.Driven`: a run of the machine under any client and any schedule,
  crashes and idle instants included. `history` is the history of round `r` in
  it.
- `GCAMachine.IsGCA`: the specification of §4.2 — in every run, every round's
  history has the six properties, and a participant that keeps taking steps
  returns. Because every finite execution is a run (`Driven.cut`), the
  properties hold of every prefix, as "for every execution" requires.
- `GCAMachine.SoloAgreement`: Solo agreement (§7), read on prefixes of runs.

## The universal constructions (§4.3, §6)

- A command `(op, i, seq)` is a `Command`; `WeakUniversal.Tagged obj` is the
  object `A_c` over commands, with the conflict relation of the underlying
  operations (`command_conflict_iff`).
- `WeakUniversal.Step` and `HelpingUniversal.Step`: Algorithms 1 and 3 as
  transition systems, one constructor per atomic step. Each step is a local
  computation followed by at most one read or write of a register `S[j]` or
  `M[j]`, or a call to or return from a GCA object.
- The pseudocode leaves some choices open: the order in which a collect reads
  the registers and, in Algorithm 3, the order of `trace(M_i)`. A rule `ch`
  (`WeakUniversal.Forward.Choices`, `HelpingUniversal.Forward.Choices`) fixes
  them, and every theorem holds for every rule.
- `WeakUniversal.Over.mrun obj G ch client sched`: Algorithm 1 run over the GCA
  implementation `G`, for a client (`client p k` is the operation of `p`'s
  `k`-th invocation) and a scheduler (`sched t`, the process that steps at `t`,
  or none). `HelpingUniversal.Over.mrun` is Algorithm 3.
- `algorithm1Over obj G`, `algorithm3Over obj G`: the implementations — the
  executions of every non-halting run, for every rule, client and scheduler. An
  operation is invoked by the step that creates its command, and completes at
  its return.
- `forward1 obj n`, `forward3 obj n`: the same algorithms over Algorithm 2 run
  as deterministic machines. Every non-halting run of them is an execution of the
  admitted model (`forward1_admitted`, `forward3_admitted`).

## Algorithm 2 (§5, Appendix A)

- `GCA.Protocol obj P`: one GCA object run by Algorithm 2 over atomic snapshot
  objects `A` and `B`: its participants and inputs, the process scheduled at each
  tick, and whether that tick completes the caller's pending snapshot operation.
  The six stages are Lines 1, 2, 3–4 (local), 4, 5 and 6–8 (local).
- `SnapshotWaitFree`: a caller that keeps taking steps completes each snapshot
  operation. It is the wait-freedom of the snapshot objects, and the only
  hypothesis of Theorem 5.1.
- `ForwardGCA.machine O n`: Algorithm 2 for every round, as a `GCAMachine`,
  run over atomic snapshot objects. It meets the specification and Solo
  agreement in every run (`machine_isGCA`, `machine_soloAgreement`).

## Linearizability

`InfEventLinearizable` is the paper's definition on a possibly infinite history
of invocation and response events: there are a completion `H̄` and a legal
sequential history `S` with `H̄|ᵢ = S|ᵢ` for every process `i` and
`≼_H ⊆ ≼_S`. The completion answers some pending invocations and drops the
others, and the real-time clause ranges over the operations it keeps. On finite
histories it is the finite definition `EventLinearizable`
(`infEventLinearizable_ofHistory_iff`).

The history of a run (`Run.events`) records the invocations and responses the run
actually made, one per step, and Theorem 4.3 and Lemma 6.1 state that it is well
formed and linearizable for every run, halting or not.

## Conflict forgetting and conflict resolution (§7)

- A finite execution `α` is the first `N` steps of a run `mrun G ch client
  sched`. An extension of it (`Over.Extends`) is a run over the same `G` that
  takes the same first `N` steps; after them the client and the rule may differ.
  The `i`-solo extension follows `α` and then schedules only `i`
  (`soloSched sched N i`).
- `Execution.EventuallyWeaklyConflictFree conflict B`: a suffix in which no two
  concurrent instances that take steps after operation time `B` conflict. The
  `N` steps of `α` end at operation time `N - 1` of the extracted execution.
- `WeakUniversal.Over.ConflictForgetting` and
  `HelpingUniversal.Over.ConflictResolving`: the paper's two definitions, read
  on every infinite extension of `α` over the same `G`.
- Conflict resolution counts operations *invoked after `α`*. The paper places
  the invocation of an operation of Algorithm 3 at the write of its command into
  `M` (Line 5). `InvocationPoint` makes that choice a parameter, and Theorem 7.2
  is stated at `.announce`, Line 5.

## Assumptions

Only the paper's model:

- **A local computation is one step.** The local trace calculations (`⊓`, `⊔`,
  compatibility, the outputs of Algorithm 2) are classical functions in general.
  They are programs for every object whose independence relation is decidable
  (`LocalCompute.ofDecidable`), every finite-state object among them, and the
  kernel evaluates the machines on them.
- **Snapshot objects.** Algorithm 2 runs on atomic snapshot objects, as the paper
  presents it. The paper relies on a wait-free linearizable implementation of
  them from read/write registers (Afek et al., 1993). The one fact this leaves
  unproved is that Algorithm 2 over such an implementation is still a
  `GCAMachine` with `IsGCA` and `SoloAgreement`. No theorem uses it: the
  theorems over any GCA take exactly those two properties as hypotheses, so a
  proof of the fact would plug in unchanged.

## Checks

Built with the library:

- `KernelAudit.lean`: fails if a module under `CFLeanProof/` is not reachable
  from `CFLeanProof.lean` (so `lake build` checks every module), or if any
  project declaration uses an axiom beyond `propext`, `Classical.choice` and
  `Quot.sound`. `Audit.lean` prints the axioms of each result stated in
  `Paper.lean`.
- Non-vacuity: the admitted sets are non-empty (`algorithm1Over_nonempty`,
  `algorithm3Over_nonempty`), the hypotheses of the §7 definitions are
  satisfiable, and concrete runs exercise contention and a stalled process
  (`ContentionWitness`, `WeakContentionWitness`), two callers in one GCA round
  (`SharedRoundWitness`), a completed operation (`LinearizationWitness`), and
  the adopt branch of Algorithm 2 (`AdoptWitness`).
- `Counterexamples.lean`: why the definitions read as they do — for instance,
  weak conflict-freedom asks for a process taking infinitely many steps, since
  an idle correct process would make it weaker than lock-freedom.
- `NonCausalWitness.lean`: Algorithm 3 needs Validity on every prefix, not only
  on the whole run. `FairnessClock.lean`: why fairness is read on the protocol
  clock.
